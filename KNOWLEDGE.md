# Intelligent Scraper — Project Knowledge Base

> A SaaS product that scrapes local business leads (name, address, phone, website, email)
> from Google Maps by industry + state + cities, sells access via subscription plans
> (Stripe), and delivers results as downloadable CSVs through a web dashboard.

Last documented: 2026-07-28. Generated by reading every file in the repo — treat this as a
snapshot, not a live source of truth; re-check the code before relying on specifics.

---

## 1. High-level architecture

```
┌─────────────────┐      HTTPS/JWT       ┌──────────────────────┐
│  Frontend (SPA)  │ ───────────────────▶ │  Backend (FastAPI)   │
│  React + Vite    │ ◀─────────────────── │  app/                │
│  Vercel-deployed  │                      └──────────┬───────────┘
└─────────┬────────┘                                 │
          │  Supabase JS SDK (auth only)              │ asyncpg (direct Postgres,
          ▼                                            │ bypasses RLS, filters by user_id
┌──────────────────┐                                   │ manually)
│ Supabase          │◀──────────────────────────────────┘
│ - Postgres DB      │
│ - Auth (JWT issuer)│              ┌──────────────────────────┐
│ - Storage (CSVs)   │◀────────────│ Worker (worker/)          │
└──────────────────┘   uploads     │ polls `jobs` table every  │
                                    │ 3s, runs Playwright scrape│
                                    │ pipeline, writes progress │
                                    │ back to Postgres           │
                                    └──────────────────────────┘

Stripe  ⇄  Backend `/billing/*` routes (checkout, portal, webhook)
```

Three deployable units, one Postgres schema (in Supabase) as the shared source of truth:

| Unit | Path | Runtime | Deploy target (per Dockerfiles) |
|---|---|---|---|
| API server | `Backend/app/` | FastAPI + uvicorn | Railway (`Backend/Dockerfile`) |
| Background worker | `Backend/worker/` | asyncio polling loop + Playwright/Chrome | Railway (`Backend/Dockerfile.worker`, base image `mcr.microsoft.com/playwright/python`) |
| Web dashboard | `frontend/` | React 18 + Vite + Tailwind | Vercel (`frontend/vercel.json`) |

Auth and billing are outsourced: **Supabase** (Postgres + Auth + Storage) and **Stripe**
(subscriptions/checkout/webhooks). The FastAPI backend does not use an ORM — it talks to
Postgres directly via `asyncpg`, and verifies Supabase-issued JWTs itself (no round trip to
Supabase for `/auth/me` etc.).

There is also a **standalone prototype script**, `scrap.py` at the repo root — see §5.

## 2. Backend (`Backend/`)

FastAPI app, Python 3.12. Key deps (`requirements.txt`): `fastapi`, `asyncpg`, `pyjwt[crypto]`,
`pydantic` v2, `httpx`, `stripe`, plus `pandas` + `playwright` for the worker.

### 2.1 App structure

```
Backend/
├── app/
│   ├── main.py        # FastAPI app, lifespan (DB pool), CORS, router wiring, /health
│   ├── config.py       # pydantic-settings, reads .env (Supabase + Stripe + DB + CORS)
│   ├── db.py           # asyncpg pool lifecycle (statement_cache_size=0 for pgbouncer)
│   ├── auth.py         # Verifies Supabase JWTs locally (HS256 legacy or RS256/ES256 via JWKS)
│   ├── deps.py         # CurrentUserDep (from Bearer JWT), DBConn (pooled connection)
│   ├── schemas.py       # Pydantic request/response models
│   ├── storage.py       # Supabase Storage REST client (upload CSV, signed download URLs)
│   └── routers/
│       ├── auth.py       # GET /auth/me, PATCH /auth/profile
│       ├── register.py   # POST /auth/register, GET /auth/check-payment (pay-first signup)
│       ├── plans.py      # GET /plans (public pricing list)
│       ├── usage.py       # GET /usage/today, GET /usage/plan
│       ├── jobs.py        # CRUD + lifecycle for scrape jobs
│       └── billing.py     # Stripe checkout/portal/webhook
└── worker/
    ├── main.py    # Poll loop + watchdog (background process, separate from the API)
    └── runner.py  # The actual 3-phase scraper pipeline (Playwright)
```

`app/main.py` wires routers with these prefixes: `/auth`, `/auth` (register shares the
prefix), `/plans`, `/usage`, `/jobs`, `/billing`. `/health` is unauthenticated. `/docs`
(Swagger) only renders when `settings.debug` is true.

### 2.2 Auth model

- Supabase issues the JWTs (via its own `/auth/v1/token` and `/auth/v1/admin/users` REST API).
- The backend **never calls Supabase to validate a token** — `app/auth.py` decodes it
  locally: HS256 with the shared `SUPABASE_JWT_SECRET`, or RS256/ES256 via Supabase's JWKS
  endpoint (`PyJWKClient`, cached 5 min). Audience is always `"authenticated"`.
- `app/deps.py` extracts `CurrentUser(id, email)` from the `sub`/`email` claims and exposes it
  as `CurrentUserDep` for any route needing auth (`HTTPBearer(auto_error=True)`).
- DB access goes through the **service-role** Postgres credentials (`DATABASE_URL`), which
  bypasses Row-Level Security. RLS stays enabled in Postgres as a safety net, but the API is
  solely responsible for scoping every query by `user_id` — see the comment in `app/db.py`.

### 2.3 Signup flow (pay-first)

Registration is Stripe-gated, not open signup:
1. User buys a plan from the public pricing page → `POST /billing/checkout` creates a Stripe
   Checkout Session (creates a Stripe customer if needed) and returns `checkout_url`.
2. On `checkout.session.completed` webhook (`app/routers/billing.py:_handle_checkout_completed`):
   - If the session has `metadata.supabase_user_id` (an existing logged-in user upgrading),
     it upserts their `subscriptions` row directly.
   - Otherwise (new customer from the public landing page) it inserts into a
     `pending_signups` table keyed by email, holding `plan_id` + Stripe IDs.
3. The user is redirected to `/signup?email=...&checkout=success`. The frontend's `Signup.jsx`
   calls `GET /auth/check-payment?email=...` to confirm a pending payment exists, then collects
   name/password and calls `POST /auth/register`.
4. `register.py`: verifies `pending_signups`, creates the Supabase Auth user via the admin API
   (`/auth/v1/admin/users`), inserts into local `users` + `subscriptions` tables, deletes the
   `pending_signups` row, then signs the user in immediately (`/auth/v1/token?grant_type=password`)
   and returns `access_token`/`refresh_token` so the frontend can call `supabase.auth.setSession(...)`
   without a second login step.
5. `GET /auth/check-payment` exists purely so the frontend can validate before showing the
   registration form.

Other subscription lifecycle events (`customer.subscription.updated/deleted`) keep the local
`subscriptions` table's `status`/`plan_id`/`current_period_end` in sync.

### 2.4 Jobs API & business rules (`app/routers/jobs.py`)

`POST /jobs` enforces, in order:
1. **Active subscription required** — joins `subscriptions` + `plans` for `status='active'`.
2. **Cities-per-job limit** from the plan (`plans.cities_per_job`).
3. **Daily lead quota** — calls a Postgres function `can_user_scrape(user_id, estimated_leads)`
   with a conservative estimate of 60 leads/city; rejects with 429 if not allowed.
4. **Concurrent-jobs limit** — counts the user's `pending`/`running` jobs against
   `plans.concurrent_jobs`.
5. Inserts a `jobs` row (`status='pending'`, `current_step='step1_maps'`) and one `job_cities`
   row per requested city (for per-city progress tracking).

Other endpoints: `GET /jobs` (respects `plans.history_days` retention window, capped at 100
rows), `GET /jobs/{id}` (job + per-city progress), `POST /jobs/{id}/cancel` (only from
`pending`/`running`), `GET /jobs/{id}/download/{file_type}` (`with_website` or `no_website`,
returns a Supabase Storage **signed URL**, 1‑hour expiry).

Jobs are **not run by the API process** — it only inserts rows. Execution is entirely the
worker's job (§2.5).

### 2.5 Worker (`worker/main.py` + `worker/runner.py`)

A separate long-running Python process (own Dockerfile, own entrypoint `python -m worker.main`).

- **Poll loop**: every 3s, looks for `jobs.status='pending'` (joined to an active subscription
  + plan to know if email scraping is allowed), respecting a **hard global concurrency cap**
  (`MAX_GLOBAL_CONCURRENT = 2` in the current code, comment says "10" — the constant was
  lowered without updating the docstring). Free slots are computed from an in-memory
  `_running: dict[job_id → user_id]`.
- **Watchdog**: every 5 minutes, force-fails any job stuck in `running` with no `updated_at`
  change for 45 minutes (comment says 20, code checks 45 — another stale comment), so crashed
  workers/power cuts don't leave jobs stuck forever.
- **Graceful shutdown** on SIGINT/SIGTERM: stops picking up new jobs, lets in-flight ones finish.

**Scrape pipeline** (`run_scrape_job` in `runner.py`), all state persisted incrementally to
`jobs`/`job_cities` so the frontend can poll progress in near-real-time:

1. **Phase 1 — Google Maps** (`current_step='step1_maps'`): for each city, launches a Chrome
   context (via Playwright `channel="chrome"`), navigates to
   `https://www.google.com/maps/search/{industry}+in+{city},+{state}`, dismisses the cookie
   consent dialog, waits for the results feed (`div[role="feed"]`), and **scrolls to the end**
   of the virtualized list (`_scroll_to_end` — polls card count until it stabilizes or the
   "You've reached the end" marker appears). Then runs an in-page JS extractor
   (`_EXTRACT_JS`) that reads each result card's name, category, rating, review count,
   address, phone, website, and the Maps detail-page URL, using a mix of CSS selectors
   (`.qBF1Pd`, `.MW4etd`, `.UY7F9`, `.W4Efsd`, `[aria-label]`, `[data-item-id]`) and regex
   fallbacks for phone/address. Blocks image/font/media requests for speed. Writes one CSV
   per city to a temp dir.
2. **Preprocess** (`current_step='step2_preprocess'`): merges all per-city CSVs with pandas,
   normalizes phone format (`+1 555-555-5555`) and address (junk-pattern filtering, `Â`
   mojibake cleanup), computes `Times_Found`/`Found_In_Cities` (cross-city duplicate
   detection by business name), de-duplicates by `(Name, Phone)` when a phone exists, and
   splits into **with-website** vs **no-website** DataFrames.
3. **Phase 2 — Detail enrichment** (`current_step='step2_enrich'`, conditional): for any
   record missing a phone or website that has a `Maps_URL`, opens that Maps detail page
   directly (bounded concurrency, `MAX_CONCURRENT_DETAIL=3`) and re-extracts
   website/phone with `_DETAIL_JS`. Backfills missing fields only.
4. **Phase 3 — Email scraping** (`current_step='step3_emails'`, only if the user's plan has
   `email_scraping=true` and there are website rows): maintains a small **pool of Chrome
   browser instances** (`MAX_CONCURRENT_EMAIL=3`, round-robin assignment, auto-recreates a
   browser if one crashes) rather than one browser per site — avoids forking hundreds of
   Chrome processes. For each business website, visits a **fixed, prioritized list of paths**
   (home, `/contact(-us)`, `/about(-us)`, `/privacy-policy`, `/terms...`, `.html` variants)
   until a "business-domain" email is found or the list is exhausted (`EMAIL_CRAWL_TIMEOUT=30s`
   per site). Email extraction (`_extract_emails_from_page`) looks at `mailto:` links, header
   text, footer text, full-body regex, and simple obfuscation patterns (`[at]`, `[dot]`, `" at "`).
   Emails are filtered (`is_valid_email` — rejects image-file-looking strings, known junk
   domains, `noreply`/`webmaster`/etc. locals, non-real TLDs) and ranked
   (`score_email`/`select_best_email` — prefers the email whose domain matches the site,
   prefers `info@`/`sales@`/`contact@`-style locals, penalizes free providers and
   dev/test-looking addresses). Progress (`emails_attempted`, `emails_found`) is written to
   `jobs` every 10 completions.
5. **Upload**: both DataFrames are serialized to CSV in-memory and uploaded to Supabase
   Storage bucket `job-outputs` at `{user_id}/{job_id}/with_website.csv` and
   `.../no_website.csv` (`app/storage.py:upload_csv`). Job is marked `status='done'`,
   `current_step='complete'`.
6. Back in `worker/main.py`, on success it calls a Postgres function
   `update_usage_after_job(user_id, total_clean, with_website, no_website, emails_found, with_website)`
   to roll the job's results into the user's daily/monthly usage counters. On any exception,
   the job is marked `status='failed'` with `error_message` (truncated to 500 chars).

### 2.6 Billing (`app/routers/billing.py`)

- `POST /billing/checkout` — creates (or reuses/repairs) a Stripe customer, starts a
  subscription-mode Checkout Session, embeds `supabase_user_id` in metadata so the webhook
  can distinguish "existing user upgrading" from "brand-new paying customer."
- `GET /billing/portal` — Stripe Billing Portal session for self-service plan management.
- `POST /billing/webhook` — verifies signature with `STRIPE_WEBHOOK_SECRET`; handles
  `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`.
  `PRICE_TO_PLAN` maps Stripe Price IDs (from env: `stripe_starter_price_id`, `_pro_`, `_elite_`)
  to internal plan ids `starter`/`pro`/`elite`. Note: `success_url`/`cancel_url` and the
  Stripe Customer Portal `return_url` are hardcoded to `http://localhost:5173` in the current
  code — will need to become env-driven before a real production cutover.

### 2.7 Config & environment (`app/config.py`)

Required: `supabase_url`, `supabase_anon_key`, `supabase_service_role_key`,
`supabase_jwt_secret`, `database_url`. Optional: `cors_origins` (comma-separated or JSON
array, default `http://localhost:5173`), `debug` (gates `/docs`), Stripe keys/price IDs
(default empty — billing routes will misbehave until set).
**No `.env.example` file currently exists** in `Backend/` even though the README references
one — worth creating if onboarding a new developer.

### 2.8 Deployment

- `Backend/Dockerfile`: `python:3.12-slim`, installs `requirements.txt`, copies only `app/`,
  runs uvicorn on port 8000. Note the `RUN playwright install chromium` line is placed
  **after** `CMD`, so it's dead code in that Dockerfile (Docker still executes every
  instruction regardless of order relative to CMD, but this looks like a copy-paste leftover
  since the API container itself doesn't run Playwright — only the worker does).
- `Backend/Dockerfile.worker`: based on the official
  `mcr.microsoft.com/playwright/python:v1.60.0-noble` image, installs deps, `playwright
  install chrome`, copies both `app/` and `worker/`, entrypoint `python -m worker.main`.

## 4. Frontend (`frontend/`)

React 18 + Vite 5 + Tailwind, deployed to Vercel (`vercel.json` does SPA rewrite to
`index.html`). No router library — routing is done by hand via `window.location.pathname`
(`/signup` vs everything else) and a `activeTab` state machine for the dashboard.

```
frontend/src/
├── main.jsx              # ReactDOM root
├── App.jsx                # Auth gate, login/forgot-password, dashboard shell + all tabs
├── components/
│   ├── ScrapeLeads.jsx     # New-job form + live job progress poller
│   ├── History.jsx         # Past jobs table with CSV download links
│   └── Signup.jsx           # Pay-first signup: email → check-payment → set password
├── lib/
│   ├── supabase.js          # Supabase JS client (anon key only, session persisted to localStorage)
│   └── api.js               # Thin fetch wrapper — attaches Supabase access_token as Bearer
```

- **Auth**: Supabase JS SDK handles login/session/password-reset directly (no backend
  round-trip for those). `App.jsx` subscribes to `supabase.auth.onAuthStateChange`. Every
  backend call goes through `lib/api.js`'s `apiFetch`, which reads the current Supabase
  session and attaches `Authorization: Bearer <access_token>`.
- **Dashboard tabs**: Dashboard (usage stat cards + daily-quota progress bar), Scrape Leads,
  History, Plan & Billing (plan comparison cards + Stripe checkout/portal buttons), Settings
  (name change, password-reset email, sign out).
- **ScrapeLeads.jsx**: chip-style city input (type + Enter/comma to add, capped at
  `plan.cities_per_job`), submits `POST /jobs`, then polls `GET /jobs/{id}` every 3s until
  the job reaches a terminal status. Shows a step bar (Maps → Process → Emails → Done),
  per-phase progress bars, a per-city status table, and download buttons once done. The
  in-flight job id is persisted to `localStorage` (`active_job_id`) so a tab switch or reload
  doesn't lose track of a running job.
- **History.jsx**: lists past jobs (desktop table + mobile card layout), download buttons for
  completed jobs.
- **Signup.jsx**: two-step form — email lookup against `/auth/check-payment` (rejects if no
  Stripe payment on file), then name/password → `POST /auth/register`, then
  `supabase.auth.setSession()` with the tokens the backend returned so the user is logged in
  immediately without a second round trip.
- Dark/light theme is toggled by setting CSS custom properties directly on
  `document.documentElement` and persisted to `localStorage("theme")` — no CSS-in-JS/theming
  library.

## 5. `scrap.py` (repo root) — standalone CLI prototype

A single-file, no-dependencies-on-the-webapp Playwright script — the **original prototype**
that `worker/runner.py` evolved from. Config is hardcoded constants at the top of the file
(`STATE_ABBR`, `INDUSTRY`, `OUTPUT_FOLDER`, `CITIES` list) — no CLI args, no DB, no auth; you
edit the constants and run `python scrap.py`.

Pipeline (`main()`): **Step 1** scrape each configured city's Google Maps results into
per-city CSVs in `OUTPUT_FOLDER` (`MAX_CONCURRENT_SITES = 20` for later email crawling) →
**Step 2** `preprocess()` merges/cleans/de-dupes into `clean_data/{STATE}_{INDUSTRY}_With_Website.csv`
and `..._No_Website.csv` → **Step 3** `scrape_emails_from_csv()` crawls each website's fixed
priority-page list for emails and writes results back into the `With_Website.csv` file.
Also includes a Facebook-page email handler (`extract_email_facebook`, tries `/about` then the
page itself) that **does not have an equivalent in `worker/runner.py`** — the production
pipeline dropped Facebook-specific handling.

Relationship to the product: functionally, `worker/runner.py` is `scrap.py` rewritten to (a)
take `industry`/`state`/`cities`/`include_emails` as parameters instead of hardcoded globals,
(b) write progress incrementally to Postgres (`jobs`/`job_cities`) instead of printing to
stdout, (c) add the Phase-2 Maps-detail-page enrichment step (not present in `scrap.py`), (d)
upload results to Supabase Storage instead of local disk, and (e) use a shared browser pool
for email crawling instead of one shared context. The core scraping heuristics (CSS selectors,
regexes, email scoring/validation, address/phone cleanup) are copied near-verbatim between the
two files — if you fix a scraping bug in one, check whether the other needs the same fix.
`scrap.py` itself appears to be kept around as a lightweight testbed for tweaking scraping
logic before porting changes into `worker/runner.py`.

## 6. Notable gaps / inconsistencies worth knowing about

- `Backend/README.md` says Phase 2/3 (`/jobs`, worker, `/billing/*`) are "not here yet" —
  that's stale; all of it is implemented. Don't trust the README's phase list.
- `worker/main.py`'s docstring says "max 10 concurrent jobs" but the actual constant is
  `MAX_GLOBAL_CONCURRENT = 2`; the watchdog docstring says "20+ minutes" but the code checks
  45 minutes. Trust the code, not the comments.
- No `.env.example` in `Backend/` despite the README instructing you to `cp .env.example .env`.
- Stripe checkout `success_url`/`cancel_url` and the billing portal `return_url` are hardcoded
  to `http://localhost:5173` in `app/routers/billing.py` — needs to be config-driven for a
  real prod deploy.
- Frontend `.env` is missing the four `VITE_STRIPE_*_PRICE_ID` vars that `App.jsx` expects for
  the plan purchase buttons.
- `Backend/Dockerfile` has `RUN playwright install chromium` positioned after `CMD` — Docker
  still runs it, but it's misleading since the API container doesn't actually use Playwright
  (only `Dockerfile.worker` does); likely copy-paste residue.
- No automated tests found anywhere in the repo (Backend or frontend).
- No CI configuration (no `.github/workflows`, etc.) found.
- The repo is **not a git repository** (no `.git` at the root) — nothing here is currently
  under version control.
- `frontend/.env` is a real (not `.env.example`) file containing a live Supabase project URL
  and anon key, and there's no `frontend/.gitignore` — `Backend/.gitignore`'s
  `frontend/node_modules/`/`frontend/dist/` rules don't cover it. The anon key is meant to be
  public-safe, but if/when this directory is put under git, add `frontend/.env` to
  `.gitignore` before the first commit rather than relying on that safety property.
- `frontend/package.json`'s `name` is still `"react-fastapi-starter-frontend"` — leftover from
  whatever generic starter template this was scaffolded from.
