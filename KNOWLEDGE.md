# Intelligent Scraper — Project Knowledge Base

> A SaaS product that scrapes local business leads (name, address, phone, website, email)
> from Google Maps by industry + state + cities, also delivers people-leads/property-owner
> data requests via an admin-fulfilled workflow, sells access via subscription plans
> (Stripe), and serves both a client dashboard and a full RBAC-gated admin console.

Last documented: 2026-08-17. Generated by reading the current repo (routers, migrations,
frontend components, tests) — treat this as a snapshot, not a live source of truth; re-check
the code before relying on specifics. Supersedes the 2026-08-02 version, which predates the
Campaign Organizer feature (§2.8, §4.1), the light/dark theme system + blue brand rebrand
(§4.3 — the prior "dark-only" claim is stale), free-form State-field input (§2.5, §4.1), and
the worker's Phase 2 enrichment progress-checkpoint fix (§2.6) — none of that existed/was true
yet at the time.

**This is a real git repository** (remote `origin`, branch `main`, real commit history) —
the previous doc's "not a git repository" note is stale.

**Hard project rule in force during active development**: all work happens against a fully
local Supabase stack (`supabase start` via Docker, `Backend/.env` points at
`http://127.0.0.1:54321`/`127.0.0.1:54322`) — nothing touches the production database,
production GitHub repo, or Railway production services until explicitly promoted.

## 1. High-level architecture

```
┌─────────────────┐      HTTPS/JWT       ┌──────────────────────┐
│  Frontend (SPA)  │ ───────────────────▶ │  Backend (FastAPI)   │
│  React + Vite    │ ◀─────────────────── │  app/                │
│  Vercel-deployed  │                      └──────────┬───────────┘
└─────────┬────────┘                                 │
          │  Supabase JS SDK (auth only)              │ asyncpg (direct Postgres,
          ▼                                            │ bypasses RLS, filters by
┌──────────────────┐                                   │ org_id/user_id manually)
│ Supabase          │◀──────────────────────────────────┘
│ - Postgres DB      │
│ - Auth (JWT issuer)│              ┌──────────────────────────┐
│ - Storage (CSVs)   │◀────────────│ Worker (worker/)          │
└──────────────────┘   uploads     │ polls `jobs` every 3s,    │
                                    │ heartbeats + watchdog,     │
                                    │ runs Playwright pipeline   │
                                    └──────────────────────────┘

Stripe  ⇄  Backend `/billing/*` routes (checkout, portal, webhook, invoices)
```

Three deployable units, one Postgres schema (in Supabase) as the shared source of truth:

| Unit | Path | Runtime | Deploy target (per Dockerfiles) |
|---|---|---|---|
| API server | `Backend/app/` | FastAPI + uvicorn | Railway (`Backend/Dockerfile`) |
| Background worker | `Backend/worker/` | asyncio polling loop + Playwright/Chrome | Railway (`Backend/Dockerfile.worker`, base image `mcr.microsoft.com/playwright/python`) |
| Web dashboard | `frontend/` | React 18 + Vite + Tailwind | Vercel (`frontend/vercel.json`) |

Auth and billing are outsourced: **Supabase** (Postgres + Auth + Storage) and **Stripe**
(subscriptions/checkout/webhooks). The FastAPI backend does not use an ORM — it talks to
Postgres directly via `asyncpg`, and verifies Supabase-issued JWTs itself. Both API and
worker are designed around a **Railway deployment model with no Docker/manual supervision**:
clients submit a request, may close their browser, and expect a finished file waiting when
they come back — this shaped the worker resilience design (§2.6).

There is also a **standalone prototype script**, `scrap.py` at the repo root — see §6.

### 2.2 Auth & platform RBAC

- Supabase issues JWTs; the backend **never calls Supabase to validate a token** — `app/auth.py`
  decodes it locally (HS256 with `SUPABASE_JWT_SECRET`, or RS256/ES256 via JWKS, cached 5 min).
- `app/deps.py::get_current_user` rejects a request the instant `users.is_active` is false —
  **on every request**, not just at login. This is what makes admin disable/suspend actions
  (§2.7) take effect immediately on a still-valid JWT, and is the reason Clients Management's
  suspend loops every org member rather than just the billing owner (access is enforced
  per-user, not per-org).
- **`platform_role`** (`users.platform_role`): `'super_admin' | 'admin' | 'client'` (legacy
  `is_admin` boolean kept for compatibility, deprecated in favor of this).
- **`admin_permissions`** table: per-admin-user granted keys — `operations_admin`,
  `people_leads_admin`, `support_admin`, `billing_admin`. Super admins implicitly hold all four.
- `app/permissions.py` exports: `SuperAdminDep`/`RequireSuperAdmin`, `AdminDep`/`RequireAdmin`
  (either admin tier), `AdminPermissionsDep` (lazy-loaded, not on the hot path), and
  `RequireAdminPermission(permission_key)` (factory, 403s if missing — super admins bypass).

### 2.3 Organizations / Teams

Every user belongs to exactly one `organizations` row (`owner_user_id` UNIQUE), joined via
`organization_members` (`role` ∈ `account_owner | client_admin | client_member`, `is_active`).
`organization_invitations` (email, role, hashed token, `expires_at`) backs the invite/accept
flow — no email-sending infrastructure exists anywhere; invite links are copy/share-only
(`app/invitations.py::build_invite_link`).

- **`organization.py`** (`/organization`) — the Team management route set: rename org, list
  members, invite/resend/cancel invitation, change member role, remove member.
  `account_owner` has full control; `client_admin` can invite/remove only `client_member`s.
  Seats are capped by `plans.max_team_seats` (starter=3, pro=10, elite=25, enterprise=∞).
- **`app/org_access.py`** exports `MyMembershipDep`/`get_my_membership` (403 if no active
  membership) and `RequireOrgRole(*roles)`, plus `get_billing_owner_id(conn, user_id, org_id)`
  — resolves whose `subscriptions` row governs a plan/limit check for a non-owner member
  (used by People Leads; `jobs.py` has its own, separate plan-check path — see its docstring
  caveat before assuming the two always agree).

### 2.4 Signup flow (pay-first)

Unchanged in shape from the original design: `POST /billing/checkout` → Stripe Checkout →
`checkout.session.completed` webhook inserts a `pending_signups` row (or upserts `subscriptions`
directly for an existing user upgrading) → frontend's `Signup.jsx` calls
`GET /auth/check-payment` → `POST /auth/register` creates the Supabase Auth user, the local
`users` row, and now also **creates the user's `organizations` row and `account_owner`
membership** as part of registration (this is new since organizations were introduced) →
returns tokens so the frontend can call `supabase.auth.setSession()` without a second login.

### 2.5 Jobs API & business rules (`app/routers/jobs.py`)

`POST /jobs` enforces, in order: active subscription (`subscriptions`+`plans` joined on
`status='active'`), cities-per-job limit, daily lead quota (Postgres function
`can_user_scrape(user_id, estimated_leads)`, ~60 leads/city estimate), concurrent-jobs limit.
Inserts a `jobs` row + one `job_cities` row per city. `GET /jobs`, `GET /jobs/{id}`,
`POST /jobs/{id}/cancel`, `GET /jobs/{id}/download/{file_type}` (signed URL, 1h expiry).
Jobs are **not run by the API process** — only the worker executes them.
`client_business.py` (`/client/business-requests`) is a sanitized, client-facing presentation
layer over this same `jobs` data that strips internal telemetry fields.

`jobs.state` / `people_lead_requests.state` are unconstrained `text` columns with **no format
validator anywhere in the backend** — the worker treats `state` as an opaque string (used
verbatim in the Maps search query and in output filenames, then stripped back out by
`_preprocess()`, so any string round-trips safely as long as it's internally consistent).
The 2-letter-only restriction that used to exist was purely a **frontend** input constraint —
`ScrapeLeads.jsx` and `PeopleLeads.jsx` now accept either an abbreviation ("FL") or a full
state name ("Florida") in the State field (placeholder: "FL or Florida"), normalized to the
2-letter code via `frontend/src/lib/usStates.js::normalizeStateInput()` right before the API
call — so `jobs`/`people_lead_requests` still always store the 2-letter form, keeping
`MyLeads.jsx`'s state filter and every existing display untouched. Unrecognized input just
passes through uppercased, matching the old behavior for anything that wasn't a full match.

### 2.6 Worker (`worker/main.py` + `worker/runner.py`)

A separate long-running process (`python -m worker.main`, own Dockerfile). Built around a
**resilience system** added after a real incident (worker silently stopped with zero
visibility; a DB outage orphaned a job in `running` forever; the pool didn't self-heal for
2+ minutes after Postgres came back) — designed for Railway, where nobody is watching and
clients expect a finished file hours later with zero manual intervention.

- **`MAX_GLOBAL_CONCURRENT = 2`** — process-local, single-instance concurrency cap (never
  designed for horizontal worker replicas; this is why `worker_heartbeats` has exactly one
  fixed row, `worker_id='primary'`).
- **`PoolHolder`** — mutable wrapper around the asyncpg pool so long-lived loops see a
  recreated pool. `.recreate()` uses `pool.terminate()` (forceful/sync, fails fast on dead
  connections — not `.close()`, which can hang) then `asyncpg.create_pool(...)` with
  `asyncio.wait_for` timeouts. Triggers after `POOL_FAILURE_THRESHOLD = 3` consecutive
  heartbeat write failures (~9s).
- **Heartbeat** (`worker_heartbeats` table, written every poll cycle): `started_at`
  (process-restart marker), `last_beat_at`, `consecutive_failures`, `pool_recreations`,
  `running_jobs` — surfaced in the admin dashboard as `worker_status`
  (healthy/degraded/down, computed from time-since-last-beat).
- **Watchdog** (`WATCHDOG_INTERVAL_S = 45`, `STUCK_THRESHOLD_MIN = 5` — evidence-based:
  worst-case legitimate per-phase time was measured against actual timeout constants, not
  guessed): finds jobs `status='running'` with no `updated_at` change past the threshold.
  Before resetting, it `task.cancel()`s any still-tracked, not-done task for that `job_id` —
  required so auto-requeue can never produce two coroutines writing the same job_id/CSV paths
  (zombie-task race). Then either auto-requeues (`retry_count < MAX_AUTO_RETRIES = 2`, via the
  shared `app/jobs_reset.py::reset_job_to_pending(bump_retry_count=True)`) or marks the job
  permanently `failed` with a real notification.
- **`reset_job_to_pending`** is shared between the watchdog and the existing admin manual-retry
  endpoint (`bump_retry_count=False` there — a human-requested retry gets a clean slate, not
  an inherited exhausted auto-retry budget).
- **Phase 1 time bound**: `CITY_SCRAPE_TIMEOUT_S = 180` wraps the per-city Maps scrape in
  `asyncio.wait_for` — without this, a dense query on a large metro could legitimately run
  past the 5-minute stuck threshold with zero DB writes and get incorrectly killed.
- **Graceful shutdown** on SIGINT/SIGTERM: stops picking up new jobs, lets in-flight ones finish.
- Logging: structured, UTF-8-safe (`sys.stdout.reconfigure(encoding="utf-8", errors="replace")`
  — a hardcoded-emoji Windows console bug bit development at one point), `%(name)s` +
  `[job {job_id[:8]}]` prefixes throughout `runner.py` (converted from bare `print()`).

**Scrape pipeline** (`run_scrape_job` in `runner.py`) — unchanged in shape from the original
design: Phase 1 Google Maps scrape (Playwright, in-page JS extractor, scroll-to-end) → merge/
clean/dedupe (pandas) → Phase 2 Maps-detail-page enrichment for missing phone/website
(bounded concurrency, `MAX_CONCURRENT_DETAIL = 3`) → Phase 3 email crawling (only if plan
allows, small Chrome-instance pool, fixed prioritized page list, scored/validated extraction)
→ upload both CSVs to Supabase Storage (`job-outputs/{user_id}/{job_id}/...`) → `status='done'`.

**Fixed 2026-08-17 — Phase 2 lacked the watchdog-safe checkpoint pattern Phase 3 already had.**
`_enrich_missing()` used to run its whole `asyncio.gather()` batch and write to `jobs` only
once, at the very end. For a job where most/all leads have no website (so most/all need a
detail-page visit), that batch can legitimately exceed `STUCK_THRESHOLD_MIN` at only 3-way
concurrency with zero intermediate `updated_at` writes — the watchdog then sees a stale
`updated_at` on a still-genuinely-working job, kills it, and (since `reset_job_to_pending`
does a **full reset**, not a resume — re-scrapes all cities from zero) burns a full Phase-1
re-run per retry before hitting the same wall again, permanently failing after
`MAX_AUTO_RETRIES`. Real incident: a 25-city/1175-lead job with 0% website rate failed this
way twice. Fix: `_enrich_missing()` now checkpoints `with_website` via `_update_job()` every
10 completions (mirroring Phase 3's existing `done[0] % 10 == 0` pattern at
`runner.py:747-756`), so `updated_at` stays fresh through a long batch.

### 4.2 Dashboard design system

`DashboardOverview.jsx` renders (top to bottom): `DashboardGreeting` (time-of-day greeting +
one of **50 real, verified-attribution quotes** picked randomly per session via
`useState(pickRandomQuote)` — not date-based), `SecureProcessingGlobe`/`SecureActivityTicker`,
usage + trend charts, composition charts, active requests/recent files. The KPI stat-card row
exists in code but is currently **hidden** behind `const SHOW_KPI_ROW = false` in
`DashboardOverview.jsx` — a deliberate, reversible toggle, not deleted code.

Charts are ECharts (`echarts` + `echarts-for-react`, `<ReactECharts opts={{renderer:"svg"}}>`)
via `components/charts/*` (`DonutChart`, `BarListChart`, `UsageRadialChart`,
`EmailDiscoveryFluidGauge`, `LeadsTrendChart`) and a shared `lib/chartTheme.js`
(`CHART_COLORS`, `resolveColor()`, literal hex constants). **Gotcha**: ECharts parses color/font
strings itself and does not resolve CSS `var(--x)` the way raw SVG DOM does — `resolveColor()`
exists specifically to bridge that, and any new chart must use it (or a literal constant) for
theme colors, never a raw `var(...)` string passed straight into ECharts option objects.
`SecureActivityTicker.jsx` uses `motion/react` (Motion, the framer-motion successor) for its
`AnimatePresence` list. `StatCard.jsx` uses `@number-flow/react` for animated numeric values.

### 4.3 Theming & UI styling

**Light/dark toggle exists** (a prior version of this doc's "dark-only, toggle fully retired"
claim is stale — a light theme was added back in a later pass, with a real toggle button and
`data-theme="light"` attribute, not just `prefers-color-scheme`). The CSS custom-property token
system lives in `frontend/src/index.css` across three `:root`/`:root[data-theme="light"]`
block pairs: **Block 1** app-wide accent tokens (~lines 1-311), **Block 2** "UI Styling &
Animated Globe" — sidebar/globe/lead-accent/status tokens (~313-812, business/people color
variants via `[data-variant]` CSS custom properties on `Sidebar.jsx`/
`SecureProcessingGlobe.jsx`), **Block 3** "Dashboard Design System" — KPI/panel/shadow tokens
(~814-1131). Dark theme uses neon glow effects; light theme swaps the same tokens to soft
shadows (glow reads muddy on white) — same structural CSS, recolored per theme, not two
separate designs. `resolveColor()` in `lib/chartTheme.js` resolves `var(--token)` to a literal
hex at render time since ECharts can't parse CSS `var()` natively (see §4.2).

**Brand accent is blue** (`--accent`: `#0F33B0` light / `#5575E7` dark), rebranded 2026-08-17
from a prior teal/violet identity to match the marketing site's palette. Every purple/indigo
token (`--brand-purple`, `--brand-purple-bright`, `--brand-indigo`) was hue-rotated to the same
227° hue with saturation/lightness preserved, so glow/tint brightness is unchanged, just
recolored. `--business-blue`/`--business-cyan` (Business-vs-People chart domain colors) and
`--people-pink`/`--people-purple` are deliberately **untouched** by the rebrand and stay
visually distinct from the new brand accent (checked: meaningfully less saturated/darker).
The animated globe illustration's `--globe-*` colors are also untouched (treated as a
self-contained icon, not UI chrome).

### 4.4 Frontend environment

`frontend/.env`/`.env.local` define `VITE_API_BASE_URL`, `VITE_SUPABASE_URL`,
`VITE_SUPABASE_ANON_KEY`. **Still-open gap** (unchanged from the prior doc): the four
`VITE_STRIPE_*_PRICE_ID` vars `Settings.jsx`'s billing UI expects are not set — "Buy plan"
buttons will show "Price ID not configured" until added.

**A real test suite now exists** (45 tests as of this writing; the prior doc's "no automated

## 7. Notable gaps / inconsistencies worth knowing about

- `worker/main.py`'s module docstring says "20 minutes"/"max 10" in places — the real values
  are `STUCK_THRESHOLD_MIN = 5` and `MAX_GLOBAL_CONCURRENT = 2`; trust the constants, not every
  comment.
- `plans.status` (added in migration `0001`) is unused dead weight — everything that checks
  "is this plan currently offered" reads `plans.is_active` instead. Don't wire new code to
  `status` without first checking whether anything actually maintains it.
- Stripe is **non-functional in local dev** (all keys blank) — refunds and any other
  Stripe-dependent admin capability from the product spec can't be built/tested locally as-is.
- **Client impersonation** and full **Package Management** (create/edit/version/archive
  subscription packages — `plans.version`/`parent_package_id`/`is_enterprise` already
  anticipate it) are both named in the product spec but have zero implementation or scaffolding
  anywhere in the codebase.
- No email-sending infrastructure exists — Team invitations and any other "send an email" flow
  are link-based/manual-share only.
- `frontend/package.json`'s `name` is still `"react-fastapi-starter-frontend"` — leftover from
  the original scaffold template, harmless but never renamed.
- `frontend/.env`/`.env.local` are missing the four `VITE_STRIPE_*_PRICE_ID` vars the billing UI
  expects.
- Recurring local-dev footgun (not a code bug): running the backend/worker via a non-activated
  venv from git-bash can spawn a process that resolves to the wrong system Python via `PATH`,
  producing confusing duplicate-looking processes on Windows. Always confirm the actually-
  listening PID (`netstat`) before assuming a code change took effect.
